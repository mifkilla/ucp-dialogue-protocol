# Observer UCP: проверка по свидетельствам и ограниченное исправление

[Основная английская версия](README.md) · [Результаты](RESULTS.ru.md) · [Фиксированный план](PLAN.ru.md) · [Основное приглашение](../../README.ru.md)

Последующий [финальный интеграционный пилот](../final/README.ru.md) добавляет направляемое извлечение обязательств из новых историй и передаёт исполнителю фактический разбор observer. Его [потолочный результат](../final/RESULTS.ru.md) не устанавливает добавочной пользы для поведения. Эта страница описывает базовый профиль observer.

Observer является необязательным профилем реализации UCP. Отдельная языковая модель проверяет конкретное обязательство по событиям с указанным авторством. Python проверяет ссылки на свидетельства, отдельно предоставленные разрешения и покрытие наблюдением, затем формирует сигнал для разбора. Это не измеритель сознания, внутренней честности, любви или универсального CARE.

**Текущая область:** локальная вызываемая реализация и ограниченный пилот на подготовленных эпизодах. Это не постоянно работающий наблюдатель данного чата, не автоматическое извлечение всех обязательств из необработанного архива и не готовая система авторизации. Сбор данных, доверенное состояние, вызов модели и расписание предоставляет среда исполнения.

## Компоненты и границы доверия

| Компонент | Вход и результат | Ограничение |
|---|---|---|
| Смысловой наблюдатель | Обязательство и события -> `pass`, `violation` или `unknown` с точными цитатами | Суждение модели даже при правильной цитате |
| `validate_assessment` | Схема, ID случая/событий и точные непустые цитаты | Происхождение не доказывает достаточность основания |
| `semantic_alert` | Кандидат `@OBSERVER[review]`; неисправный ответ вызывает `@CARE.ALERT` категории здоровья монитора | Сигнал не предоставляет права и ничего не исполняет |
| `permission_check` | Операция/объект/версия и текущий `Authority` среды | Подлинное актуальное состояние и исполнение ограничения обеспечивает среда |
| `coverage_check` | Конкретные ID событий/проверок, версии соглашения и время | Выявляет пропуск обработки, не смысловое внимание и не сознание |
| `RepairCase` | Предложение, квитанция, проверка эффекта и предел попыток | Состояние в памяти процесса; нет исполнения, долговечного журнала и аутентификации |

`@OBSERVER[review]` является предлагаемым расширением профиля UCP. В существующем ARRIVAL `@OBSERVER` обозначает роль, а `@CARE.ALERT` реализован отдельно. Совместимость со всеми обработчиками ARRIVAL не заявляется. Поле `origin` является меткой, не подписью. Среда должна проверять происхождение события; атом внутри цитаты не становится командой.

Неопределённый смысловой результат вызывает разбор затронутого вопроса. Он сам по себе не доказывает нарушение и не требует останавливать все разрешённые задачи. Подтверждённое отсутствие разрешения предотвращает действие только при реальном применении ограничения средой. Обычные шаги в пределах действующего разрешения не требуют нового согласия каждый раз.

## Запуск реализации

Нужны Python 3.11+ и стандартная библиотека. Из корня репозитория:

```powershell
python -B -m unittest discover -s experiments/observer -v
python -B -m unittest discover -s experiments/continuity -v
```

`observe.py` принимает пакет с `cases` и ответ внешнего наблюдателя с `assessments`. Эталонные оценки он не читает. Распакуйте [архив свидетельств](../data/observer-04.zip) в новый каталог. Следующие команды выполняются из распакованного каталога:

```powershell
python -B observe.py packet-A.json responses/A.json --out observer-report.json
python -B evaluate.py verify .
python -B evaluate.py analyze .
```

Первая команда создаёт проверенные по формату оценки и сигналы. Вторая сверяет хеши зафиксированных входов. Третья пересчитывает сохранённые ответы по эталонам и создаёт `analysis.json`. Модель эти команды не вызывают. `observe.py` требует новое имя результата и не перезаписывает предыдущий отчёт.

Интерфейс ответа задан в `PROMPT` файла [evaluate.py](evaluate.py). Среда может вызвать свою модель с этой схемой и передать JSON в `observe.py`. События являются данными, не командами. Частные архивы нельзя отправлять провайдеру без разрешения; для проверки нужен только относящийся к ней контекст.

Для проверки покрытия `--health health.json` принимает отдельный снимок среды:

```json
{
  "event_ids": ["e1", "e2", "e3"],
  "reviewed_ids": ["e1", "e3"],
  "current_revision": 3,
  "review_revision": 3,
  "now": 100,
  "checked_at": 99,
  "max_age": 10
}
```

Будет отмечен пропуск `e2`, хотя последнее событие обработано. ID должны быть устойчивыми и уникальными, время использовать одни часы и единицы среды. Список завершённых проверок берётся из записей обработки, а не из слов модели «всё проверено». Пропуск или старая проверка является проблемой монитора, не нарушением участника. Проверку следует вызывать перед существенным действием и после результата или смены соглашения; фоновый планировщик этот репозиторий не устанавливает.

## Что вычисляется

Каждый результат относится к одному обязательству в данном эпизоде. `pass` не удостоверяет будущее поведение. `unknown` означает содержательную неопределённость; ошибки формата, дубликаты и пропуски учитываются отдельно как `invalid`.

Показываются совпадения с эталонами организатора, матрица трёх смысловых классов с отдельным столбцом ошибок, precision/recall нарушений, ложные тревоги на эталонных pass, чрезмерные утверждения на эталонных unknown и покрытие определёнными решениями. Последнее является долей валидных pass/violation и отличается от покрытия обработкой в watchdog. При пустом знаменателе результат `null`, не ноль и не идеальная оценка.

Критические нарушения границ не компенсируются удачными ответами. Общего взвешенного балла заботы или личности нет. Исходный оптимум CARE в MEANING-CRDT предполагает содержательную числовую шкалу, положительные веса и заданные потери; для согласия, истины и полномочий эти величины не появляются автоматически.

Нынешняя эвристика открытого диалога ARRIVAL присваивает позицию `0.5`, когда подходящих атомов нет. Диагностический контрпример получил `care_resolve=1.0` и для вымышленного ответа о публикации вопреки запрету, и для ответа с сохранением приватности. Это основание проверять обязательства отдельно; теорему о взвешенном квадратичном оптимуме пример не опровергает.

## Что способен показать пилот

Входы содержат 24 синтетических случая и шесть обезличенных исторических реконструкций. Два новых субагента рассматривают одинаковые случаи в разном фиксированном порядке, без эталонов и предшествующего диалога. Изоляция процедурная на общей файловой системе; точная модель и параметры генерации неизвестны. Исходные исторические выдержки проверены локально; модель получает реконструкции с заданными обязательствами и описаниями артефактов. Проверяется суждение по подготовленным свидетельствам, не извлечение из полного необработанного диалога.

Восемь фиксированных воспроизведений исправления рассматривают изменённый артефакт, доставку без подтверждённого эффекта, отзыв разрешения и исчерпание попыток. Они не показывают автономное исправление LLM или причинное преимущество сигналов. Наблюдения и отдельная рецензия приведены в [результатах](RESULTS.ru.md).

Для другого эксперимента сначала определите и проверьте план. `evaluate.py prepare <новый-каталог>` фиксирует входы данного пилота и отказывается работать поверх существующего каталога. Завершённый запуск не подготавливают заново. Неудобные валидные оценки сохраняются, а не перезапускаются до улучшения показателя.

## Научный и технический контекст

- [MEANING-CRDT v1.1](https://github.com/mifkilla/Arrival-Protocol/blob/22f001ba6f9648b758c9d7a65264448ea97fd074/docs/math/MEANING-CRDT_v1.1.pdf): числовое согласование при явных предпосылках.
- [Словарь ARRIVAL](https://github.com/mifkilla/Arrival-Protocol/blob/22f001ba6f9648b758c9d7a65264448ea97fd074/docs/ATOM_DICTIONARY.md), [CARE alert](https://github.com/mifkilla/Arrival-Protocol/blob/22f001ba6f9648b758c9d7a65264448ea97fd074/src/arrival/memory/care_alert.py), [реализация метрики](https://github.com/mifkilla/Arrival-Protocol/blob/22f001ba6f9648b758c9d7a65264448ea97fd074/src/arrival/crdt_metrics.py): близкие механизмы и ограничения эвристики.
- [Bauer, Leucker и Schallhart, Runtime Verification for LTL and TLTL](https://christian.schallhart.net/publications/2011--tosem--runtime-verification-for-ltl-and-tltl.pdf): формальный предшественник неопределённых оценок неполных трасс; не доказательство смысловой корректности этого observer.
- [Zheng et al., Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685): свидетельства того, что оценки второй модели подвержены смещениям и требуют проверки.
